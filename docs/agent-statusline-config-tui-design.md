# agent-statusline 設定 TUI 基本設計

状態：基本設計（実装前）
対象：`agent-statusline config`（対話的な設定エディタ）
前提となる仕様：[agent-statusline-spec.md](agent-statusline-spec.md)

2026-10-12 の壁打ちドラフト（GUI・Starship 設定支援）を、レビューを踏まえて基本設計へ整理したものである。コード上の根拠は、コミット `87f40a2` 時点のソースを確認した結果に基づく。

## 1. 目的

使える部品を選び、行と順序に沿って並べ、見た目を確認しながら設定できる環境を提供する。TOML や `format` の構文を最初から覚えなくても、次のことを気軽に試せるようにする。

- どんな部品があり、それぞれがどんな表示になるか
- 絵文字・色・閾値・並びを変えると、全体がどう見えるか
- 状態（コンテキスト警告、クォータ逼迫、レビュー待機など）や端末幅が変わると、どう見えるか

利用者は開発者（まず作者自身）である。ただし「開発者向けだから使いにくくてよい」とはしない。操作は発見しやすく、効果が即座に目に見えることを要件とする。TOML の直接編集も引き続き可能で、TUI は直接編集した内容を壊さない。

## 2. スコープ

| 区分 | 内容 |
|---|---|
| 対象 | `agent-statusline` 自身の `config.toml` の編集、プレビュー、安全な保存 |
| 対象外（別設計） | Starship 設定の編集、シンボリックリンクの作成・診断・復旧、クラウド同期の管理、設定の環境差分合成 |
| 対象外（恒久） | 専用クラウド、アカウント機構、自由座標配置、実端末の完全再現 |

Starship 対応は、設定モデルも描画経路も別なので、本設計に含めない。必要になった時点で、この設計の中核（§5 の編集サービス）を再利用できるかを検討し、別の設計書を起こす。

## 3. 設計判断

### 3.1 UI 方式：ターミナル UI（TUI）を採用する

壁打ち時点の第一候補は Tauri だったが、次の理由で `ratatui` による TUI に変更する。「GUI でも TUI でもよい。直感的にプレビューでき、気軽に試せること」を満たす案を、技術負債の少なさを最優先として比較した。

| 観点 | TUI（ratatui） | egui / eframe | Tauri＋Web UI | ローカル Web UI | JSON Schema＋既存エディタ |
|---|---|---|---|---|---|
| 絵文字・幅・色の再現 | 実際に使う端末そのもの | 独自描画で端末と乖離 | xterm.js でも端末と乖離 | 同左 | プレビューなし |
| SSH・WSL・リモート上で使えるか | 使える | 使えない | 使えない | ポート転送が必要 | エディタ依存 |
| 配布 | 既存の単一バイナリのまま。self-updater・installer・release に変更なし | 単一バイナリだが GUI 依存が増える | WebView2 / WebKitGTK、別ビルド系統 | 単一バイナリ＋静的アセット | 追加なし |
| 依存と保守 | 純 Rust のクレート 2 つ前後 | 中 | Tauri、npm 系、フロント一式の Renovate 追従 | 中 | 小 |
| 直感的な操作 | キー操作＋マウスクリック。ドラッグ＆ドロップは弱い | 良い | 良い | 良い | 弱い |
| 試行のしやすさ | 良い | 良い | 良い | 良い | 弱い |

採用理由は次のとおり。

1. **プレビューの忠実さが最大の価値**である。このツールの出力は端末向けの ANSI 文字列で、絵文字の幅・フォント・配色の見え方こそ設定の勘所になる。TUI は、その端末でそのまま確認できる。GUI で端末表示を模擬すると、本設計が避けたい「見た目の乖離」を自分で作り込むことになる。
2. AI CLI は SSH 先、WSL、コンテナなど、GUI を持たない環境でも動く。そこで設定を直せる。
3. 部品は約 10 個、format は `$name` の置換と改行だけという小さな構成に対し、Web フロントエンド一式と WebView 依存を持ち込む保守コストは釣り合わない。
4. 弱点は、ドラッグ＆ドロップとカラーピッカーの直感性である。キー操作の一貫性、マウスクリック、色・スタイルのプリセット選択で補う。

UI を GUI へ替える可能性は残す。§5 の編集サービスと §4 の描画の分離は UI に依存しないので、将来 GUI を追加する場合も、同じ中核の上に別のフロントエンドを載せるだけで済む。

### 3.2 クレート構成：単一クレートを維持する

Cargo workspace への分割は行わない。TUI も同一バイナリのサブコマンド（`agent-statusline config`）とし、`release.yml`、`verify-release-assets.sh`、インストーラー、self-updater の asset 名を変更しない。

- 依存の追加は `ratatui`、`crossterm`、`unicode-width` 程度を見込む。いずれも純 Rust で、システムライブラリを要求しない。
- `render` の起動速度（既定レイアウトで Linux 約 2ms、Windows 約 11〜16ms）と、リリースバイナリのサイズを、実装前後で計測する。劣化が許容できない場合に限り、`tui` feature を導入して既定ビルドから分離する。計測前に feature を切らない。
- `src/main.rs` と `src/cli.rs` は、行数のラチェット（`scripts/check-code-behind-size.ps1`）の対象である。サブコマンドの追加では引数定義とディスパッチだけを置き、上限の引き上げは同じ PR で理由を説明する。

### 3.3 保存の正本は設定ファイル

TOML ファイルを正本とし、TUI 内の配置モデルは編集時の派生表現とする。設定全体を型へ読み込んで再シリアライズすると、コメントや未知の項目を失う。そこで元の `toml_edit::DocumentMut` に、変更したキーだけを書き込む。

## 4. 描画の分離（前提リファクタリング）

プレビューを実現するには、現行の描画から副作用を切り離す必要がある。

### 4.1 現状の問題

| 箇所 | 内容 |
|---|---|
| `formatter.rs` の `render_template` | 描画の途中で `get_git_status`（gix によるリポジトリ読み取り）と、`render_review_for_repo` 内の `load_summary`（サマリ JSON の読み込み）を呼ぶ |
| 同 | 部品ごとに `config.format.contains("$x")` の分岐と `.replace` の連鎖があり、部品の追加では描画・Config・GUI 用の定義の 3 か所を更新することになる |
| 同 | 置換が逐次的で、先に置換した結果の文字列が後続の置換対象になる（たとえば、ブランチ名に `$model` が含まれると再展開される）。モジュールの `format` 内も同様で、`$folder_style` を `$folder` より先に置換するなど、順序への依存がある |
| `main.rs` の `cmd_render` | 更新確認（`check_update_background_if_needed`）と Squirrel Notifier への書き出しは `cmd_render` 内にあるため、`render_template` を直接呼べば実行されない |
| `config.rs` の `load_config` | パース失敗・読込失敗のとき、`eprintln!` してから `Config::default()` を返す |

### 4.2 分離の方針

描画を「入力の収集」と「合成」に分ける。

```text
収集（副作用あり）: stdin JSON → StatuslineState ／ cwd → GitStatus ／ サマリ → ActiveReview, QueuedReview
合成（純関数）   : compose(config, state, git, review, width) -> String
```

- `render` は、収集してから `compose` を呼ぶ。出力はこれまでと同一であること。
- TUI は、収集を行わず、シナリオ（§6.3）のサンプル値を `compose` へ渡す。したがって、プレビューのために Git、サマリ、更新確認、Notifier 出力が実行されることはない。
- `compose` 内の置換は、1 パスで解釈する方式にそろえる。字句規則は次のとおりとする。
  - `$` に続く文字列は、**その文脈で既知の変数名**（トップレベルの `format` では部品 ID、モジュールの `format` ではその部品の `placeholders`）のうち、最も長く一致するものとして読む。識別子として読める範囲全体は使わない。
  - 変数名の直後の文字列は、固定テキストとして保つ。たとえば既定の `context.format` の `$symbolCtx` は、`$symbol` と固定テキスト `Ctx` に分かれ、現行どおり `🧠 Ctx` と表示される。
  - 既知の変数名に一致しない `$xxx` は、そのまま出力する（現行の `.replace` も置換しない）。
  - 既存の出力と一致する範囲では挙動を変えない。逐次置換でしか起こらない再展開（置換済みの文字列に含まれる `$model` が、後続の置換で展開される、など）だけを、バグとして扱い、直す。
  - `$symbolCtx` と、変数名の直後に英数字が続くカスタム設定（`$tokensX`、`$folder_styleY` など）を、回帰テストに含める（§9）。
- 「CLI の既存出力を変えない」ことは、ゴールデンテストで担保する（§9）。

### 4.3 設定の読み込み

TUI 用に、失敗を返す読み込み API を別に用意する。

```text
load_config_strict(path) -> Result<LoadedConfig, ConfigError>
LoadedConfig { config: Config, document: DocumentMut, source: ConfigSource }
ConfigSource = Existing { path: ResolvedPath, fingerprint: ContentHash }
             | Missing  { target: PathBuf, from_link: bool }   // まだ作られていない。履歴・ハッシュは持たない。from_link はリンク切れのリンクを辿って決めた保存先か（§5.4）
```

- 既存の `load_config` は、`render` が「設定が壊れていても止まらない」ために現状のまま残す。
- 構文エラーの場合、TUI は元の内容とエラー位置を表示する。既定値で上書きせず、保存も受け付けない。選択肢は、(a) `$EDITOR` で開く、(b) 何もせず終了、の 2 つに限る。
- 設定ファイルがまだ存在しない場合は、`ConfigSource::Missing` として既定値で開始する。保存先 `target` は、`--config` または `AGENT_STATUSLINE_CONFIG` があればそのパス、なければ `dirs::config_dir()/agent-statusline/config.toml` とする。`resolve_config_path` はファイルが存在しない場合に `None` を返すため、保存先を決める関数を別に用意する。
- 標準パスが、リンク先のないシンボリックリンク（リンク切れ）の場合も `Missing` とし、`target` は `read_link` で解決したパスにする（相対リンクはリンクの親ディレクトリを基準にする）。`canonicalize` は対象が存在しないとエラーになるため、`Missing` の解決には使わない。

## 5. 部品レジストリと編集サービス

### 5.1 部品レジストリ

部品の定義を、宣言的な 1 か所にまとめる。これを、描画の分岐、TUI の部品一覧、プロパティ編集、検証の共通の根拠にする。

```text
PartSpec {
    id,                 // "git_branch"。`$git_branch` と config のテーブル名に対応
    props: [PropSpec],  // 編集できるキー
    render,             // 収集済みの入力から、その部品を描画する関数
    // 以下は TUI（フェーズ 1）で、使う側と同時に追加する
    // label, category（§6.2）, visibility（§6.5）, sample
}
PropSpec { key, kind }  // default は Config::default() から得る。suggestions は TUI で追加する
kind = Symbol | Style | Threshold | Text | Bool | Separator | Choice(values) | Format(placeholders)
```

- `format` 文字列の変数は、部品単位ではなくキー単位で持つ（`Format(placeholders)`）。`review` は `format`・`active_format`・`waiting_format` で使える変数が異なるため。
- `Threshold` の範囲は 0〜100 の整数。`threshold_warning < threshold_critical` の検証は編集サービス（§5.3）で行う。
- `[directory] truncation_mode` は `left`（先頭側を省略: `.../foo/bar`）と `middle`（中間を省略: `/foo/.../bar`、既定）から選ぶ（`Choice`）。認識できない値でも描画は止めず `middle` として扱い、保存時の検証がエラーにする。

レジストリには、次の整合を保つテストを置く。

- `Config::default()` を TOML にしたときのすべてのキーが、レジストリの `props` に存在する（Config に項目を足したのにレジストリへ足し忘れる、を検知する）。
- 部品 ID は、他の部品 ID の接頭辞にならない。トップレベルの `format` では `$context_x` のような固定テキストの扱いが部品の追加で変わるため、これを防ぐ。モジュール内の変数名は、`$folder` と `$folder_style` のように接頭辞の関係があってよい（§4.2 の最長一致で解決する）。
- 各部品の既定の `format` が使う変数は、その `Format` の変数に含まれる。
- 既定のトップレベル `format` が使う部品 ID は、すべてレジストリに登録されている。

これは TUI がなくても、描画の重複を減らす価値のあるリファクタリングである。

### 5.2 配置モデルと `format`

`format` は、行（`\n` 区切り）と、行内の並びで構成される。§4.2 の字句規則に従い、`$部品ID`（既知の部品 ID の最長一致）と、それ以外の文字列（空白、区切り記号、固定テキスト）に分解でき、連結すれば元の文字列に戻る。部品 ID の直後に続く文字は、固定テキストになる。

```text
Layout = [Line]
Line   = [Token]
Token  = Part(id) | Literal(String)
```

- 現行の描画には、条件付きグループなどの複雑な構文はない。したがって、`format` はすべて上の形で、**損失なしに**往復できる。読み込んだ `format` が GUI で表せない、という状況は、現行の仕様では起こらない。
- 認識できない `$xxx` は、描画でもそのまま出力される（置換されない）ので、`Literal` として保持し、プレビューと検証で警告する。
- 改行は行の境界として表し、独立した部品にはしない。部品一覧の「改行を追加」は、行境界の挿入操作とする。
- 描画は、空になった行を出力から除く（`render_template` は空の行を出力しない）。配置領域では、行内の部品がすべて非表示になる行を、その旨を添えて示す（§6.5）。

### 5.3 TOML の部分更新

| 操作 | 書き込む内容 |
|---|---|
| 配置の変更 | トップレベルの `format` だけを更新する |
| プロパティの変更 | 対象テーブルの対象キーだけを更新する。キーがなければ追加する |
| 既定値と同じ値に戻したとき | 元ファイルにそのキーがなければ書かない。あれば、その値に更新する |
| 触れていない項目 | コメント、並び、未知のキーを含め、そのまま残す |

- `format` の書き方（`"""` の複数行か、`\n` を含む 1 行か）は、元の表現を引き継ぐ。引き継げない場合は、既定の README 例と同じ複数行形式で書く。
- 未認識のキー（`symbl` のような綴りの誤りを含む）は、`Config` が `deny_unknown_fields` ではないため、CLI は無視する。TUI は、レジストリと照合して警告として示す。書き換えはしない。
- 保存前に、(1) 再解析できること、(2) `Config` として読めること、(3) 閾値の範囲（`threshold_warning < threshold_critical` など）、(4) スタイル名が `parse_style_tokens` で認識できること、を検証する。
- スタイル指定（`parse_style_tokens`）は、現在 16 色の名前と `bold`・`dimmed`・`italic`・`underline`・`inverted` に限られる。256 色や RGB への拡張は、エンジンの変更を伴うので、本設計の範囲外とする。

**編集中の状態（`editor/draft.rs`）**：TUI は、設定の `Draft`（元の `DocumentMut`、そこから導いた `Config`、配置の `LayoutEditor`、検証の結果）を操作する。プロパティの変更は、候補の文書を作って `validate` にかけ、エラーがなければ採用する（エラーの値は受け付けず、下書きを変えない。警告は受け付けて表示する）。配置とプロパティの変更は、時系列で 1 本の履歴に積み、`undo` で操作の逆順に戻す（§6.3）。保存用の TOML は、配置が `format` と異なるときだけ `set_format` で書き込む。

### 5.4 保存・外部変更・履歴

設定ファイルは、クラウドドライブ上の実ファイルへのシンボリックリンクであることがある。TUI は、リンクの作成や診断を行わないが、その構成を壊さずに保存できなければならない。

保存は、読み込み時の `ConfigSource` によって 2 通りに分かれる。

**`Existing`（既存ファイルの更新）**

1. **保存先**：`fs::canonicalize` で解決した実ファイルに書く。標準の設定パス（リンク）は置換しない。
2. **書き込み**：実ファイルと同じディレクトリに一時ファイルを書き、`rename` で置換する。失敗した場合は旧内容を保ち、エラーを表示する。通常ファイルのコピーに黙って切り替えない。
3. **競合検知**：読み込み時の内容ハッシュを保存直前に再計算して比較する。変更されていた場合（削除された場合を含む）は上書きを止め、「再読み込み」「差分の確認」「別名で保存」を選べる。ファイル監視は補助にとどめ、保存直前の再確認を省略しない。
4. **履歴**：保存前の内容を、ローカルのデータディレクトリ（`dirs::data_local_dir()/agent-statusline/history/`）へ世代保存する。保持数は 20 世代とする。クラウド側の履歴と二重にならないよう、履歴自体は同期の対象にしない。復元は、差分を示してから行う。複数の設定ファイルの履歴が混ざらないよう、実ファイルのパスのハッシュ（先頭 8 バイトの 16 進）でサブディレクトリを分ける。`installer/patcher.rs` のバックアップ処理は、保存先と対象が異なる（クライアントの設定 JSON のバックアップ）ため再利用せず、`editor/history.rs` に別実装した。

**`Missing`（初回保存）**

1. **保存先**：`target`（§4.3）をそのまま使う。`canonicalize` は使わない。親ディレクトリがなければ作成する。ただし、リンク切れのリンクを `read_link` で解決した `target` の親ディレクトリが存在しない場合は、作成せずにエラーを表示する（クラウドフォルダの未同期・未マウントを、空のディレクトリで隠さないため）。
2. **競合検知（存在しないことの確認）**：保存時にファイルが作られていた場合は上書きしない。一時ファイルを `target` と同じディレクトリに書き、`hard_link` で `target` に公開する（既存なら `AlreadyExists` で失敗し、一時ファイルを削除する）。`hard_link` が使えないファイルシステムでは、`OpenOptions::create_new` で `target` に直接書く（このとき書き込み中の内容が他のプロセスから見える可能性があることを、制約として明記する）。`AlreadyExists` になった場合は、`Existing` の競合時と同じ「再読み込み」「差分の確認」「別名で保存」を選べる。
3. **履歴**：旧内容がないので、履歴は作らない。初回保存の内容は、次回の保存時に旧内容として履歴へ残る。
4. 保存に成功したら、`ConfigSource::Existing`（保存した内容のハッシュ）へ切り替える。

どちらの場合も、次の共通の規則に従う。
- **ヘッダーでの表示**：解決した設定ファイルのパスと、リンク先（リンクの場合）を常に表示する。未作成の場合は、「未作成（保存すると作成されます）」と保存先を示す。標準パスと、`--config` または `AGENT_STATUSLINE_CONFIG` で指定されたパスが異なる場合は、どちらを編集しているかを明示する。

クラウド同期中の競合や同時編集は、ハッシュだけでは完全に防げない。その限界を前提に、履歴と差分で復旧できることを重視する。

## 6. 画面と操作

### 6.1 画面構成

```text
┌ プレビュー ─ 幅: [auto|80|120|160]  シナリオ: [通常 ▾]  実環境: off ┐
│ 📁 myproject [~/src/myproject] 🌿 main ✗ 🔒 sandbox                   │
│ 🤖 Claude Opus  🧠 Ctx: 72% (62k tok)  working                        │
```

- プレビューは常に最上部に置き、操作の結果が即座に見えるようにする。
- 端末が狭いときは、部品一覧とプロパティを切り替え表示にする。
- 主要な操作は、画面下部のキー一覧と `?` のヘルプで常に確認できる。マウスでのクリック（フォーカス移動、選択、ボタン）にも対応する。

### 6.2 部品の分類

| カテゴリ | 部品 |
|---|---|
| 作業場所・Git | `directory`、`git_branch`、`git_status` |
| エージェント | `model`、`context`、`agent_state`、`plan`、`quota`、`sandbox` |
| レビュー | `review` |
| レイアウト | 空白、区切り文字、固定テキスト |

各部品は、名前と、現在の設定・選択中のシナリオで描画した短い表示例を並べて示す。説明や詳細な設定は、選択してから開く。実際に使える部品だけを表示し、未対応の分類を空のまま見せない。

### 6.3 部品を試す（仮挿入プレビュー）

「気軽に試せる」ことを最優先の体験とする。

- 部品一覧でカーソルを動かすと、その部品を配置領域のカーソル位置へ**仮に挿入した状態**をプレビューに表示する。確定（`Enter`）するまで設定は変わらない。
- 行内でカーソルを動かす、部品を入れ替える、といった操作の結果も、確定前に同じ仕組みで見える。
- 仮挿入は、配置のカーソル（選択中のトークン）の**後ろ**に入れた状態を見せる。確定は `Enter`（後ろ）と `i`（前）で、前に入れた結果は、確定後に見える。
- プレビューと部品の表示例は、ratatui を介さず**生の ANSI** で端末へ直接出す。ratatui の色の指定は 256 色の指標になり、太字の明るさが `render` の出力と食い違うため（0-4b の実機確認）。毎回全体を描き直し、枠の内側に収まるよう幅と行数を切り詰める。
- すべての変更は元に戻せる（`u`）。保存するまでファイルには書かない。

### 6.4 絵文字と記号

`symbol` などの記号は、次の 2 通りの入力を提供する。

1. **候補から選ぶ**：部品ごとに用意した候補（例：Git は 🌿 🌱 🔀 ⎇、エージェントは 🤖 🧠 ⚡ など）と、共通の記号一覧から選ぶ。ASCII のみの代替も候補に含める（絵文字が崩れる端末向け）。
2. **自由に入力する**：任意の文字列（複数の絵文字、Nerd Font のグリフ、ASCII）を直接入力・貼り付けできる。

どちらの場合も、入力した記号の**表示幅**（`unicode-width` による）を示す。幅が端末によって変わりうるもの（異体字セレクタ、ZWJ で結合された絵文字、East Asian Ambiguous など）には注意を表示する。プレビューは実際の端末で描画されるので、崩れた場合はその場で気づける。

`directory` は、`symbol` キーを持たず、📁 が `format` の文字列に埋め込まれている。部品間で編集の体験をそろえるため、`[directory] symbol`（既定 `"📁 "`）の追加を提案する。既定の `format` を `$symbol[$folder]($folder_style) …` に変えるが、既存の出力と既存ユーザーの設定は変わらない（§11 の決定事項）。

### 6.5 非表示条件の見える化

部品の中には、条件を満たさないと何も出力しないものがある。配置領域では、その部品を薄く表示し、理由を添える。

| 部品 | 非表示になる条件 |
|---|---|
| `git_branch`／`git_status` | Git リポジトリの外／変更がないとき（`git_status`） |
| `agent_state` | 状態が `idle` のとき |
| `review` | Squirrel Notifier の連携が無効、または該当する PR がないとき |
| `quota` | クォータ情報がないとき |
| `model`／`context`／`plan` | エージェントの入力に該当するデータがないとき |
| 共通 | `disabled = true` のとき |

実表示のプレビューは、この条件に従って出力する。行内のすべてが非表示の行は、描画から除かれるので、配置領域には「この行は出力されません」と示す。

### 6.6 プレビューの幅

- 「幅」は、`compose` に渡す端末幅（現在は `directory` のパス省略にだけ効く）と、折り返しの模擬幅を兼ねる。`auto`（実端末の幅）、80、120、160、任意の列数を選べる。
- 幅より長い行は、実端末ではエージェント CLI 側の表示方式（折り返し、切り詰め）で変わる。プレビューは、「折り返す」「切り詰める」の 2 通りを切り替えて確認できるようにする（折り返しは、ANSI を保つ自前の処理で、表示幅は `unicode-width` で計算する）。
- 指定した幅が実端末より広いときは、その旨を表示して横を切り詰める。

### 6.7 シナリオ

プレビューは、実環境から独立した、あらかじめ用意したサンプル状態で描画する。

| シナリオ | 内容 |
|---|---|
| 通常 | 標準的な状態 |
| 長いパス・ブランチ | 省略の挙動を確認する |
| コンテキスト警告／上限間近 | `threshold_warning`／`threshold_critical` による色の変化 |
| クォータ逼迫 | 複数のクォータ、リセットまでの時間 |
| レビュー待機／実行中 | `review` の表示 |
| エージェント待機 | `idle` と `working` の差（部品の非表示条件） |

「実環境」モードは、明示的に選んだときにだけ、カレントディレクトリの Git 状態を収集する（読み取りのみ）。更新確認と Notifier への書き出しは、どのモードでも実行しない。

### 6.8 プロパティの編集

- 色：`Style` 型は、色（前景・背景）、`bold`・`dimmed`・`italic`・`underline`・`inverted` をトグルで選ぶ。選んだ結果の文字列（`bold cyan` など）を併記する。
- 閾値：数値の増減で調整し、`warning < critical` を満たさない値は受け付けない。変更するとプレビューが即座に変わる。
- `format`（詳細）：変数（`$symbol` など）を補完しつつ、文字列として編集できる。未知の変数や、`[text](style)` の括弧の不整合は警告する。
- TOML 表示：現在の変更差分を、TOML のまま確認できる。TOML を直接編集した結果の再読み込みにも対応する。再解析して、TUI で扱えない構造が見つかった場合は、その場所を示し、元の文字列を保持する。

## 7. モジュール構成（案）

```text
src/
├── engine/
│   ├── parts.rs     # 部品レジストリ（PartSpec、PropSpec）。描画・TUI・検証の共通の根拠
│   ├── template.rs  # `$name` の字句解析と 1 パス展開
│   ├── formatter.rs # 部品ごとの描画、`compose`（純関数）、`collect`（収集）
│   └── …            # 既存の config / style
├── editor/       # LoadedConfig、配置モデル、TOML の部分更新、検証、保存、履歴
├── preview/      # シナリオ（サンプル状態）、幅・折り返しの模擬
└── tui/          # ratatui による画面と入力。editor / preview / parts を呼ぶだけに保つ
```

`tui/` に業務ロジックを置かない。状態遷移（操作 → 新しい状態）は、画面から独立した関数として書き、端末なしでテストできるようにする。ファイルシステム、時刻、環境変数は、インターフェース越しに渡し、テストで差し替えられるようにする。

## 9. 検証計画

既存の方針（パラメータ化されたテスト、依存の差し替え）に従う。

| 対象 | 確認内容 |
|---|---|
| 描画の維持 | 代表的な設定とシナリオの組（既定、全部品、無効化、長いパス、警告・上限）で、分離前後の出力が一致するゴールデンテスト |
| 字句規則 | 既定の `context.format`（`$symbolCtx`）が `🧠 Ctx` のまま表示される。変数名の直後に英数字が続くカスタム設定（`$tokensX`、`$folder_styleY`）、未知の `$xxx`、`$folder` と `$folder_style` の接頭辞関係、置換済みの文字列に `$model` を含む場合（再展開されない）をパラメータ化して検証する |
| 描画の副作用 | `compose` が Git・サマリ・更新確認・Notifier に触れない（入力を渡すだけで描画できる） |
| レジストリ | §5.1 の整合テスト |
| 配置モデル | `format` ⇄ `Layout` の往復が文字列として完全に一致する。未知の `$xxx` と空行を含む |
| TOML の部分更新 | コメント、未知のキー、`format` の書式、キーの並びが保たれる。既定値の扱い（§5.3）。壊れた TOML を上書きしない |
| 保存（既存） | リンク先への保存でリンクが残る。保存の失敗で旧内容が残る。外部変更・削除を検知して上書きを止める。履歴の保持数と復元 |
| 保存（初回） | 設定ファイルも親ディレクトリもない状態から保存でき、履歴を作らない。保存直前に他のプロセスがファイルを作った場合に、上書きせず競合として扱う。リンク切れのリンクは、リンク先の親ディレクトリがあれば `target` に作成し、リンクが残る。リンク先の親ディレクトリがなければ、作成せずにエラーにする。保存後に `Existing` へ切り替わり、次の保存で履歴が作られる |
| 状態遷移 | 追加・移動・削除・元に戻す・仮挿入が、画面なしでテストできる |
| 画面 | `ratatui` の `TestBackend` で、主要な画面のスナップショットを確認する |
| 実環境 | Windows／Linux、WSL、複数の端末、絵文字のフォント、実際の AI CLI での表示、クラウド同期フォルダ上の設定 |

実端末との差は、代表的な環境での手動確認とする。

## 10. 既知の限界

- プレビューは、TUI を動かしている端末での表示である。AI CLI が statusline を表示する領域（幅、フォント、折り返し）は、これと異なることがある。実際の CLI での最終確認は残る。
- ドラッグ＆ドロップによる並べ替えは提供しない。キー操作とマウスのクリックで同じことができるようにする。
- カラーピッカー（256 色・RGB）は、エンジンが対応していないため提供しない。
